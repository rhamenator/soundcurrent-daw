# Native restoration dependency reports

The four restoration helpers now have a separate dependency-report capture path. It consumes the checked staged payload using explicit collection and candidate receipt pins, then invokes the host's `readelf --dynamic --wide` on Linux or Visual Studio `dumpbin /nologo /dependents` on native Windows. The inspector reads image metadata; helpers are not executed by this step.

The reports are raw evidence for later dependency-closure review. They do not claim complete dynamic-load discovery, transitive dependency closure, corresponding dependency source, standalone installation, package admission, installed GUI acceptance, or release qualification. All those authority flags remain false. `nativeExecutionPerformed` refers to the helpers, not the native inspector process. Default preview application inventories remain unchanged.

Each inspector has a 30-second process-and-drain work deadline and independently bounded stdout/stderr retention of at most 1 MiB each, with no shell invocation. Cleanup allows at most five additional seconds for owned-process termination and half a second for pipe-reader joins. Reader threads never write report files and close their own pipes; the calling thread never waits on a pipe close. A reader still blocked after cleanup causes refusal. On Windows this may leave a daemon reader until an inherited pipe handle closes or the collector exits; descendant termination is not guaranteed. On POSIX an inspector group is killed on failure; successful reports do not attest descendant cleanup. Failure, timeout, excessive output, changed helper/candidate/inspector bytes, or inventory mismatch leaves `reports.pending.json`; the final `reports.json` is published only after all four successful reports and readback. The selected inspector path is resolved (including normal system readelf symlinks), and the resolved inspector binary hash, helper byte pins, command/result records and all 16 report-file hashes are retained. The inspector is a trusted installed build tool; its recorded hash is evidence, not an independent authenticity attestation. The output contains exactly 17 files. This is point-in-time capture, without an atomic snapshot or crash-durability guarantee.

The collector's optional `--dependency-output` requires `--stage-output`; `--dependency-tool` is accepted only with report output. Non-owning Linux shards return before collection, staging and report capture. The owning Linux shard and native Windows main desktop suite retain reports alongside the original collection and staged payload. Windows resolves `dumpbin.exe` beside the configured native CMake linker, because the preceding command shell's developer environment does not persist into PowerShell.

Standalone capture uses `tools/restoration_dependency_reports.py --candidate DIRECTORY --output NEW_DIRECTORY --expected-source COMMIT --collection-sha256 PIN --candidate-sha256 PIN` and an optional `--inspector PATH`. Capture requires the actual native host platform. Producer-selected pins prove consistency only; independent exact-head Linux/Windows execution, original artifact integrity, report semantics and reviews remain merge requirements.

The retained-report reader accepts `--verify-reports DIRECTORY --candidate DIRECTORY --platform linux|win32 --expected-source COMMIT --collection-sha256 PIN --candidate-sha256 PIN --reports-sha256 PIN`. All three receipt pins are caller supplied. It checks the original 17-file inventory, strict JSON keys and types, all report hashes and extents, four role/image bindings, native command shape, successful bounded result records and final readback, with the staged payload verified before and after. It runs no inspector or helper, writes no report files, and can inspect the other platform's retained layout. Recorded build-machine paths need not exist on the reader's machine. File checks are point in time, without a concurrent-writer snapshot or independent inspector authenticity claim.

Owning CI paths exercise this reader on their actual native reports and retain a separate `restoration-worker-dependency-verification.json`; it is outside the unchanged 17-file report inventory. Producer-computed pins demonstrate consistency only. Independent original-artifact and native-workflow audits remain required, and successful reading grants no dependency-closure, source, package, installer or GUI authority.
