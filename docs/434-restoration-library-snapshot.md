# Selected library candidate snapshots

`tools/restoration_library_snapshot.py` copies explicitly selected candidate bytes into a new artifact directory after the shared binding reader checks all report, candidate, collection, selection and source pins. It does not choose libraries by searching a loader path. The same 64-file, 64-MiB-per-file and 128-MiB-total limits apply. Existing destinations, linked parents and output beneath a checked report or candidate directory are refused.

Each copy uses bounded reads, checks the pinned source before and after copying, flushes the new file and checks its complete bytes again. Before publishing, the tool verifies the original bindings again, compares retained selection and binding bytes, checks every copied file and refuses unexpected or linked entries. Interrupted or refused work retains pending evidence and never publishes a successful final receipt. This is point-in-time byte consistency, not an atomic filesystem snapshot, power-loss durability qualification or authorization to reuse later changed files.

The final directory contains `snapshot.json`, the original pinned `selections.json`, `bindings.json` and one `file-NNN.bin` per selected file. The snapshot receipt binds the context, original selection hash, retained binding hash, ordered selected file names/extents/hashes and remaining unbound names. Pending receipts are not successful snapshots. No helper, inspector or selected library executes during this operation.

Both owning native CI paths select one explicit libsndfile candidate: Linux uses the native build's `SNDFILE_LIBRARY` cache entry and records its canonical file path; Windows uses the DLL from the existing native sndfile build. The producer records a consistency pin and retains the complete candidate bytes and receipts separately from the unchanged 17-file report and 22-file helper payload directories. Other dependency names remain unbound. Independent qualification must compare those original retained bytes, pins and direct-report names on both platforms; synthetic tests alone do not qualify the native candidate snapshots.

Arbitrary candidate bytes remain permitted. This does not establish SONAME or DLL identity, ABI, loader selection, transitive or dynamically loaded closure, source or distribution rights, standalone/package admission, installer or installed-GUI qualification. Those flags remain false. Default preview inventories and delivered packages are unchanged; full corresponding-source, licensing, native installation and frozen product acceptance requirements remain open.

The CLI takes the binding reader's report/candidate/platform/source/collection/candidate/report/selection arguments plus `--output NEW_DIRECTORY`. It prints its receipt only after publication succeeds. The output directory is an artifact of an explicit copy request; the original selected source is not changed.

Output overlap compares canonical paths on both sides, after refusing linked output parents and existing or linked output entries. This includes Windows short-name aliases; comparing an unresolved output spelling against a resolved input can miss the overlap ([Python pathname documentation](https://docs.python.org/3.14/library/os.path.html#os.path.realpath)). Refusal happens before creating the output directory, preserving the checked input's inventory.
