# Native manifest-only source stage

`SavedManifestStage` is a separate I/O-owned proof for a saved project with no
existing recovery journal. It does not construct a historical restoration audit.
The caller supplies the original source ticket, a fresh native manifest audit,
the actual checker report/PID, a freshly approved source handle, independently
captured current context and a fresh operation. The writer PID must be this
native process; all owners share the same admitted memory scope.

Before destination mutation, the original ticket and source are reverified, a
fresh finite replacement decode is performed, and the actual decoded extent/hash
must match the checker. A planned record binds the current owner and exact
manifest asset. Missing canonical media is required. The destination must match
the original native stamp; an operation directory is created exclusively with
the existing bounded stage primitive. Cancellation can leave partial evidence;
it never authorizes publication or cleanup of unrelated files.

The stage retains the original audit, source, planned record and staged native
handles. Reverification checks the exact original-to-owned parent transition,
the named root, original pinned and named manifest/canonical observations,
planned intent, staged bytes and source bytes. It never rebases the audit stamp.
Ordinary manifest audit verification remains strict. The file-only check is
private to this typed stage and is bracketed by the owned transition checks.

There is no public commit method, controller command, worker transport, current
controller permit, automatic project adoption or restart capability. Live worker
dispatch must still consume the original private preparation/control frame,
establish current owner and distinct actual job identities, hold parent pins
through launch/reap and honor cancellation/close/permission ordering. Publication
must refuse existing or conflicting canonical media. Native handles belong only
on the I/O worker, never in a control-thread completion or snapshot.

The actual-checker-backed stage cases cover an admitted stage and move, exact
record/bytes, retained and released native pins/credits, wrong PID/context/scope,
changed source/root, byte and memory limits, cancellation before mutation and
during transfer, already-present canonical media, reused operations, a different
destination and an unrelated mutation after staging. Existing validators,
deadlines and test inventory remain unchanged. Exact-head Linux and native
Windows execution, Codex/Claude review and original evidence retention are still
required before integration; source inspection alone does not qualify runtime.
