# Explicit dependency file bindings

The direct dependency inventory records names. A selected file is a separate claim: it may have the wrong ABI, identity, version, source or distribution rights. `tools/restoration_library_bindings.py` binds explicitly selected local file bytes to known lookup names without claiming that the runtime loader would use those files.

Supply the existing report, candidate, collection and source pins, plus a pinned selection JSON. Its exact fields are `format` (`sc-restoration-library-selections-v1`), `sourceCommit`, `nativePlatform`, `collectionSha256`, `candidateSha256`, `reportsSha256` and `files`. Each file has exactly `lookupName`, `path`, `bytes` and `sha256`. A lookup name must occur in the verified direct inventory and appear at most once in the selection. Windows lookup keys use the inventory's lowercase spelling. The path is an explicit absolute local path; it need not match the lookup basename, so alias choices remain visible rather than inferred. No search path, environment or current-directory search chooses a file.

Selections may be partial or empty; `unboundNames` preserves every unselected name. The bounds are 64 files, 64 MiB per file, 128 MiB total and 1 MiB of selection JSON. Files and path components must be plain and unlinked. Reads are bounded and compare opened-file identity, extent, timestamps and SHA-256 with the supplied pins. The tool verifies the inventory again, reads back the selection, and checks each selected file again before returning. This is point-in-time byte consistency, not an atomic filesystem snapshot or authorization to copy a later changed file.

The API and CLI run no inspector or helper, load or copy no library, and write no files. The CLI adds `--selections FILE --selections-sha256 PIN` to the direct inventory's report/candidate/source/platform/three-pin arguments and prints JSON after complete success. Candidate bytes need not be an executable image. The output explicitly denies loader-resolution, ABI, licensing, transitive/dynamic-load closure, dependency-source, standalone/package, installer and installed-GUI qualification. Default preview inventories and delivered packages are unchanged. Native-library identity and resolution evidence, corresponding source and rights, checked staging, and clean installed execution remain required before dependency distribution.

File identity, extent and modification time agree across path and opened-handle checks. Change-time comparisons stay within each API: path stat before/after and handle fstat before/after. Some Windows Python versions expose different meanings for those APIs' `st_ctime_ns`; equating the two rejects unchanged files ([CPython issue157671](https://github.com/python/cpython/issues/157671)). Changes within either API remain refused, and the byte pins and full final readbacks remain mandatory.

The owning Linux shard and native Windows test suite exercise the shared API and CLI using synthetic candidate bytes, including refusal and change cases. They establish the file-binding contract on the native host; they do not qualify a real dependency set. Existing original-artifact integrity and exact-head review gates remain required.
